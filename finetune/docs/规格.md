# PrivShield 第三层 · 数据与训练规格

**本文件是唯一规范源。** 任何字段名、数字、阈值只在这里定义一次,其他文档和代码不得复制,只能指向。

**冻结规则:** 「标签体系」「gold 数据格式」「质量验收标准」三节在**数据生成开始前定稿**,之后不得修改。改了等于所有已生成数据作废。其余小节可迭代。

---

## 一、这一层做什么

后端 `llm_adapter.py` 的 `verify_with_llm()` 一次调用、一个 JSON 返回两件事:

- **`decisions` 复核** —— 对上游给的候选(`status == "pending"` 或 `conflict`)判定留/不留、类别、把握
- **`additions` 补漏** —— 在可见窗口里找出上游完全没提到的实体

已实测:当前上游(规则 + NER-LITE,`ner_enabled=False`)在 CLUENER dev 1343 条上精确率 25.4%、**召回率 3.4%**,PERSON 召回 **0.0%**(`CN_PERSON_PATTERN` 只匹配「我叫X」「姓名:X」「联系人:X」三种句式)。**所以 `additions` 承担绝大部分工作量,这一层实质是主力 NER。**

边界纠错通过 **reject + add** 表达(`decisions` 没有 start/end 字段),不需要改后端。

**不做的事:** 打码替换、知识图谱、`parse_instruction_with_llm`、跨句准标识符组合。

## 二、标签体系

九个标签,与后端 `EntityType` 一致(去掉 `CUSTOM`):

```
PERSON  ORG  LOCATION  ADDRESS  PHONE  EMAIL  ID_CARD  BANK_CARD  PASSPORT
```

**排除 `CUSTOM` 的理由:** 它由运行时用户规则填充,分数恒为 1.0 直接采纳,永远不会成为候选。生成它等于教模型幻觉。

**边界口径(不得由代理自行解释):**

| 判据 | 规则 |
|---|---|
| ADDRESS vs LOCATION | 能定位到门牌的完整地址(含区县 + 路街号)是 **ADDRESS**;地名、行政区、地标是 **LOCATION**。与后端 `ADDRESS_PATTERN` 对齐 |
| 英文样本的 ID_CARD | **不使用。** 后端正则是 `\d{17}[\dXx]`,中国身份证专用。英文文本里的等价物匹配不上,塞进去等于教模型输出下游接不住的东西 |
| ORG 的范围 | 指**可独立识别的机构实体**：公司、学校、医院、政府机关、社会组织。**不包括机构内部的部门名**（产品部、销售部、人事部、财务部、技术部等）——它们不识别任何人或任何机构，且后端实测完全不产生候选。这类词应作为 hard_negative 的陷阱，不得标注为 ORG。 |

单批注入 **4 个**标签(9–15 个标签的推荐值)。注入过多会让单条文本 PII 密度失真。

## 三、gold 数据格式

JSONL,每行一条。**这是冻结对象。**

```json
{
  "id": "syn_zh_mid_000123",
  "lang": "zh",
  "text": "报修人张伟，联系电话13812345678。",
  "spans": [
    {"start": 3, "end": 5, "label": "PERSON"},
    {"start": 10, "end": 21, "label": "PHONE"}
  ],
  "trap_spans": [],
  "kind": "positive",
  "meta": {"domain": "设备维修工单", "format": "工单系统条目",
           "tone": "正式书面", "tier": "中"},
  "gen": {"model": "deepseek-v4-pro", "batch": "b0007",
          "seed": 42, "ts": "2026-08-20T09:00:00Z"}
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | str | `syn_{lang}_{tier_code}_{6位序号}`，tier_code 为 ASCII：短密=dense / 短=short / 中=mid / 长=long。**id 不得含非 ASCII 字符**（会进文件名、manifest 键、日志）。切分、去重、把评测错误追回源头的唯一依据 |
| `lang` | str | `zh` / `en` / `mixed` |
| `text` | str | 剥离标签后的纯文本 |
| `spans` | list | 半开区间 `[start, end)`,按 `start` 升序。`text[start:end]` 必须等于实体原文 |
| `trap_spans` | list | 刻意埋设的陷阱,格式 `{start, end, text, trap}` |
| `kind` | str | `positive` / `hard_negative` / `true_negative` |
| `meta` | dict | 生成时的轴取值,审计时定位「哪个场景组合产出质量差」 |
| `gen` | dict | 生成溯源。多模型混合时回答「哪家产出的坏样本」 |

**`split` 不写进本文件。** 单独一步按 `hash(id)` 确定性分配,可审计、可重算。

**四个新增字段的判据是「事后程序算不出来的才记」:**

- `id` —— 事后按行号补,一重排就失效
- `lang` —— 可启发式反推,但**生成意图**和**反推结果**不一致(中文句里嵌一个英文人名算 zh 还是 mixed?)
- `trap_spans` —— `kind` 是样本级的,陷阱是**具体某串在某位置**。有它才能报「服务号误判类陷阱误报 3.2%」,而不是笼统的「精确率 94%」
- `gen` —— 事后完全无法恢复

### 换行符与哈希（跨平台硬约束）

本机 Git 的 core.autocrlf 会把 LF 换成 CRLF。数据生成在 Windows、
训练在 Linux，因此：

1. **所有数据文件一律 `path.write_bytes(payload)`，禁止 `write_text()`。**
   `write_text()` 在 Windows 上按平台换行，同一份数据会得到不同 SHA-256。
2. **所有 SHA-256 一律对归一化后的 LF bytes 计算：**
   `hashlib.sha256(content.replace(b"\r\n", b"\n")).hexdigest()`
   包括 gold 数据、manifest、以及派生层记录的后端文件指纹。
3. 读取时统一 `newline=""` 或直接读 bytes 自行 split。

## 四、生成机制:内联标记

模型直接在正文里打标签,**偏移在剥离标签的过程中累加得到**:

```
模型输出   报修人<PERSON>张伟</PERSON>联系<PERSON>张伟</PERSON>，电话<PHONE>13812345678</PHONE>。
解析结果   报修人张伟联系张伟，电话13812345678。
spans      [{3,5,PERSON}, {7,9,PERSON}, {12,23,PHONE}]
```

**为什么不让模型自己报 offset:** token/字符不对齐,LLM 报的偏移不可靠。

**为什么不用事后 `text.find()`:** 值重复出现时 `find()` 返回首个匹配,未必是标注者所指。上例两个「张伟」拿到 3 和 7 两个不同偏移,`find()` 做不到。

实现见 `finetune/scripts/primitives.py` 的 `parse_inline_tagged()`。**该函数已通过七项自检,不要重写。**

**任何解析异常一律抛错,上层丢弃重生成,禁止修复。**

## 五、多样性保障(五项,必须全部实施)

单一 prompt 重复调用会导致严重模式坍缩。

### 5.1 轴采样

四轴组合空间 ≥ 10 × 8 × 4 × 4 = **1280 种**,取值见 `finetune/configs/axes.yaml`。

**那四个列表由人编写,不由代理生成。** 代理写出来的会很平,直接压低多样性上限。

label_group 是允许标签池，不是必现清单。部分档位的建议实体数小于组内标签数，强制必现会导致无解。

### 5.2 长度分档(最关键,最容易被忽略)

实测背景:合成集文本中位数 43–121 字符、PII 密度每千字符 50.9 个;真实文本(Kaggle PIILO 学生作文)中位数 3524 字符、密度 **0.1** 个,且 **86.1%** 的真实文档不含任何 PII。**差两个数量级。**

#### 表 A · 生成目标区间（写进 prompt 的目标，允许重叠与缺口）

| 档 | tier_code | 中文/mixed | 英文 | 建议实体数（软目标） | 权重 |
|---|---|---|---|---|---|
| 短密 | dense | 50-160 | 150-400 | 4-6 | 0.05 |
| 短 | short | 50-150 | 150-400 | 1-3 | 0.25 |
| 中 | mid | 300-800 | 700-1100 | 2-6 | 0.40 |
| 长 | long | 1500-3000 | 1500-3000 | 0-3 | 0.30 |

这是「让模型往哪写」的目标，不是判据。建议实体数仅写进 prompt 作为软目标，
不作为 gold 层的硬性验收门槛。

长档的价值不在于文档级稀疏（实测传不到窗口），而在于：
`routed_context` 按风险关键词选句，会把「提到地址/电话但不给出具体信息」
的句子也选进窗口。实测某长文档窗口 8 句中有 4 句属于此类。这是线上最
容易误报的场景，且只有长文档才产生——短文档走 1200 字 fallback，
全文可见，没有筛选过程。

#### 表 B · 实测归类切点（按语种覆盖完整允许区间的唯一判据）

第一步，按字符数定基础档：

| 中文 / mixed | 英文 | 档 |
|---|---|---|
| 40-200 | 40-450 | 短 |
| 201-1199 | 451-1199 | 中 |
| 1200-4000 | 1200-7500 | 长 |

1200 这个切点不是随意取的：它是 `routed_context` 的 fallback 阈值。低于它整段可见，高于它才触发窗口选择——这是唯一功能性有意义的边界，且与语种无关。

第二步，短档内按实体数区分：

归入「短」且实体数 ≥ 4 → 改判为「短密」。

（短密与短长度相同，区别在密度，光靠字符数无法区分。）

第三步，统一校验实体数与密度：

| 判据 | 上限 |
|---|---|
| 密度 | ≤ 60 个/千字符 |
| 绝对数 | ≤ 25 个 |
| **单个可见窗口内** | ≤ 15 个（受 max_tokens=1200 约束，保持不变） |

不再按档设置不同的实体数上限。分类仍用「短档内实体 ≥ 4 → 短密」。

用 bake-off 数据校验：deepseek 长/zh（2922 字/17 实体/5.8 千分比）通过；
deepseek 中/zh（196 字/12 实体/61 千分比）拒绝；两者都符合人工判断。

#### 丢弃条件（仅三条）

| 语种 | 允许字符区间 |
|---|---|
| 中文 / mixed | 40 – 4000 |
| 英文 | 40 – **7500** |

理由：英文同等信息量约需 2.5–3.8 倍字符，4000 的上限是按中文定的，
会把合格的英文长档误杀。7500 的上界由训练序列预算反推，见「训练配置」。

1. 字符数超出对应语种的允许字符区间
2. 实体密度或绝对数超出上表上限
3. 解析失败

**tier=长 的请求返回短文本不再丢弃**，按实测归入中或短即可——它仍是一条稀疏度良好的合格样本。长档配额不足由批次调度补齐。

**文中要自然地出现若干句子，提到「地址」「电话」「联系人」「邮箱」
这类词，但并不给出具体的个人信息。例如「请把地址发给我」「那个电话
一直没打通」「联系人还没定」。这类句子和真正含个人信息的句子应当
交替出现。**

长档超出 `routed_context` 的 1200 字 fallback,**强制模型从非零起点的窗口里工作**——这是最难、也最有价值的训练信号。

短密档专门对齐前端内置演示样例的形态（75–142 字、每条 5 个实体、PII 密度 35–65 个/千字符）。它刻意违反本规格『质量验收标准』第 4 项的密度上限，因此审计时该档单独统计，不计入总体密度指标。

#### routed_context 的切句行为（本项目已修改后端）

原实现的切句正则 `[。！？!?\n]` 不含英文句号，导致整段英文被视为
单个句子原样进入 prompt。实测：12000 字符的英文文档 prompt 约
3123 token，加上 max_tokens=1200 共 4323，**超过部署时的
--max-model-len 4096，请求会直接失败**。

已修改为 `[。！？!?\n]|\.(?=\s)`：英文句号仅在其后为空白时才算句末。
这样邮箱 a.b@c.com、小数 3.14、文件名 x.v2.pdf 不会被切碎。

修改前后实测：

| | 修改前 | 修改后 |
|---|---|---|
| 英文 2000 字符可见率 | 100% | 11% |
| 英文 12000 字符 prompt | 3123 token | 409 token |
| 某长档 gold 实体可见 | 7/7 | 2/7 |

**代价：英文由此获得了与中文相同的路由召回上限。** 这不是模型能力
问题，评测时必须与模型漏检分开归因。短文本（演示样例的 75–142 字）
走 1200 字 fallback，不受影响。

队友的 32 个后端测试在修改后全部通过。

### 5.3 一次调用产出多条

| 档 | 每次调用产出 |
|---|---|
| 短 | 8 条 |
| 中 | 4 条 |
| 长 | **2 条** |

模型能看到自己前面写的几条,会主动求变,比多次单条调用更省钱也更多样。

### 5.4 温度不下调

`temperature = 1.0`。**多样性靠高温度获得,稳定性靠事后校验保证。** 调低温度直接导致句式坍缩。

### 5.5 去重

| 范围 | 判据 |
|---|---|
| 批内 | 字符 4-gram Jaccard **< 0.35**(≥ 0.35 即拒绝) |
| 与已有全部批次 | 文本完全一致即拒绝 |
| **跨 split** | 5-gram Jaccard **< 0.6** ← 见「切分与冻结」 |

## 六、语种与样本性质配比

| 维度 | 配比 |
|---|---|
| 语种 | 中 50% / 英 30% / **中英混合 20%** |
| 样本性质 | positive 70% / hard_negative 20% / true_negative 10% |

**中英混合那 20% 不是凑数:** `routed_context` 里同时含中文和拉丁字母的句子**无条件判为风险句**,是这个系统里被路由命中率最高的一类文本。

**prompt 里必须有 locale 硬约束**,否则中文样本里会混入大量纯拉丁的姓名/地址/日期(参照实测 17.5%)。

## 七、硬负样本与陷阱

`hard_negative` 样本里埋入「长得像 PII 但不是」的串,并在 `trap_spans` 记录位置和类型。陷阱清单见 `finetune/configs/axes.yaml` 的 `traps`。

**`trap_spans` 里的位置必须准确**,它是评测时归因误报类型的唯一依据。

其中「型号/订单号像护照号」这一类特别重要:后端 `PASSPORT` 正则是 `[A-Z]{1,2}\d{6,9}`,极宽,是现成的高价值误报陷阱。

---

## 八、结构化 PII 生成

**模型不写号码。** 模型在正文里写占位符,程序在解析偏移**之前**替换,替换后的长度自然进入最终偏移,不需要二次平移。

必须使用 `finetune/scripts/primitives.py` 里已验证的生成器:

| 函数 | 保证 |
|---|---|
| `make_id_card()` | MOD 11-2 正确,后端 `_cn_id` 通过 200/200 |
| `make_bank_card()` | Luhn 正确,后端 `_luhn` 通过 200/200 |
| `make_phone()` | 匹配 `1[3-9]\d{9}` |
| `slot_rng(seed, id, slot)` | 同 id 可复现,不同 id 不同 |

**端到端已验证:100 组结构化 PII 全部被规则层精确检出(边界完全一致)。**

**校验位分布：85% 正确 / 15% 故意错误。**

校验位正确的那部分（85%）：规则层以 0.97 采纳 → 不会成为候选 →
模型应当学会「不重复 add 已被上游采纳的实体」。

校验位故意错误的那部分（15%）：正则形态匹配但校验函数拒绝 →
规则层**静默丢弃** → 不产候选 → **模型必须 add**。

依据是实测：队友前端 Workbench.tsx 的内置演示样例「客户服务记录」里，
银行卡号 6222021001116247 的 Luhn 余数是 9（需为 0），规则层完全漏掉。
真实文本中打错、编造、测试用的号码普遍存在，这正是第三层要补的一类。
两种情况都必须在训练数据中出现，否则模型只会其中一半。

### 上游已知行为：ID_CARD 与 BANK_CARD 的跨类型混淆

后端 BANK_CARD 正则是 12–19 位数字 + Luhn。18 位身份证只要碰巧
Luhn 通过就会撞上，实测触发率约 10%（400 个里 39–40 个）。两种形态：

| 身份证校验位 | Luhn | 规则层行为 | 第三层该做什么 |
|---|---|---|---|
| 正确 | 不过 | ID_CARD 0.995 accepted | 不重复 add |
| 正确 | 通过 | ID_CARD 0.995 **conflict=True → pending** | decisions 判 keep=true |
| 错误 | 不过 | **静默丢弃** | additions 补上 |
| 错误 | 通过 | 误判成 **BANK_CARD** | decisions 判 keep=false，再 add 正确类型 |

**这是上游的真实行为，生成器不得规避、不得特殊处理。** 它是
decisions 通道的一个系统性训练数据来源——conflict=True 会让候选
无视 0.82 阈值直接进入候选列表。

mixed 语种的 PASSPORT locale 随机按 70% 使用 `zh`、30% 使用 `en`，同时覆盖中国主体与外籍主体。

## 九、三道校验

### 9.1 机械校验

半开区间、`text[start:end]` 与实体原文一致、无重叠、标签在枚举内、`trap_spans` 位置有效。

### 9.2 标签扩展与漏标扫描

**重复出现由程序扩展，不要求模型重复标注。**

后端落地用 find-all（见「唯一的后端改动」），敏感串的每次出现都会被打码；评测口径是 (surface, label) 集合。因此模型只需把每个不同的串标一次，程序负责扩展：

    对每个已标 (surface, label)：
        用 primitives.find_all(text, surface) 取全部出现位置
        包含守卫：若某次出现被一个【更长的】已有 span 完全包含，丢弃它
                  （例：ADDRESS「上海市浦东新区世纪大道88号」内部的
                    LOCATION「上海」不应单独成 span）
        其余全部写入 gold.spans

实测：一条含重复实体的样本扩展出 7 个 span，全部与原文一致，无重叠冲突。

**SWEEP 的能力边界（必须如实记录）：**

SWEEP 使用 `from app.recognizers import PATTERNS`，而后端对 PERSON / ORG / LOCATION 的召回实测仅 3.4%。因此：

| SWEEP 能可靠抓到 | SWEEP 抓不到 |
|---|---|
| PHONE / EMAIL / ID_CARD / BANK_CARD / PASSPORT 的漏标 | PERSON / ORG / LOCATION / ADDRESS 的漏标 |

实测例：「我是小陈，来自东北，同事李海燕在长春。手机13800138000，邮箱a@b.cn。」SWEEP 只抓到 PHONE 和 EMAIL，小陈/东北/李海燕/长春全部漏过。

**所以人名、机构名、地名的漏标只能靠人工审阅**，这是 pilot 60 条全检与放量后抽样 100 条不可省略的直接原因。

SWEEP 命中未标注的结构化 PII → 该样本丢弃重生成（结构化 PII 是确定性可测的，做硬门槛安全）。

### 9.3 人工语义审阅

**机械校验只能证明格式对,证明不了语义对。** 两个不可省的时点:pilot 60 条**全检**;放量后**抽样 100 条**。

审阅发现的问题**不要逐条正则化成永久硬断言**(见 `AGENTS.md`)。

## 十、质量验收标准

**第 3、4、5 项是合成数据最容易不合格的三项,且互相关联(都由长度分档控制)。**

## 十一、切分与冻结

| split | 条数 | 用途 |
|---|---|---|
| train | 3200 | 训练 |
| dev | 400 | 选 checkpoint、调参 |
| **test(冻结)** | **600** | 按 语种 × 长度档 分层抽样 |

生成总量 5000,预期净剩约 4200(畸形丢弃 + 去重损耗 15–20%)。

**冻结动作必须在训练开始之前完成:**

1. 按 `hash(id)` 确定性分配 split
2. **跨 split 5-gram Jaccard 去重(阈值 0.6)** —— 同一生成器出的数据跨 split 必有近重复,只做批内去重不够。**不做这一步,冻结测试集的数字会虚高,答辩一问就塌**
3. 写 `manifest.json`:SHA-256、条数、分布、冻结时间戳
4. manifest 进版本库(数据本身不进)

**冻结后不得用于调提示词、调超参。调参用 dev。**

## 十二、派生层契约

**生成一次,派生 N 次。生成脚本不该知道 `llm_adapter.py` 的存在。**

理由:SFT 样本不是文本的属性,是「文本 × 流水线状态」的属性。prompt 里的 `context` 依赖 `routed_context`,`candidates` 依赖 `ner_enabled` 和阈值——**全是队友的、而且一定会变**。烤进生成文件,队友一开 BERT NER 就全部作废、重新花钱;隔开则重跑派生几秒钟。

`derive_sft.py` 是**纯函数**,对每条 gold:

1. 跑真实上游 `detect_rule_spans` + `detect_lite_ner_spans` + `merge_spans`
2. `candidates = [s for s in spans if s.status == "pending" or s.conflict]`
3. `context = routed_context(text)`,解析出可见区间
4. **按可见区间裁剪 gold** —— 窗口外实体从 target 剔除(gold 文件里原样保留)
5. 算 target:
   - `decisions` —— 逐候选对照 gold 判 `keep` / `label`
   - `additions` —— 窗口内、未被已 accepted span 覆盖的 gold 实体,**带正确绝对偏移**。additions 按 (surface, label) 去重，同一个串只输出一次（取窗口内首次出现的偏移）。理由：后端 find-all 会把该串的所有出现一并打码，重复输出纯属浪费 token，且与评测口径不一致。
   - `certainty` —— 结构化 PII 校验通过 + 边界清晰 → `high`;与 `trap_spans` 相邻或类型有歧义 → `medium`。**不能全是 `high`**
6. 渲染 chat template:`enable_thinking` 用默认值,prompt 结尾是 `<|im_start|>assistant\n`,**target 是纯 JSON、不带 think 块**
7. 输出 `{id, source_id, messages, derive}`

`derive` 记两样:用的阈值,以及**依赖的后端文件 SHA-256**(`recognizers.py` / `llm_adapter.py` / `schemas.py`)。队友一改后端,脚本立刻报「训练数据过期」。

### 第 4 步为什么不能省

实测:一条 1435 字的长文档,`routed_context` 只选中 2 段共 43 字(**3.0%**),5 个 gold 有 2 个模型**根本看不到**。不裁剪就是训模型凭空捏造。

### 双阈值

| 阈值 | 占比 | 效果 |
|---|---|---|
| **0.82**(仓库真实配置) | 70% | 候选稀少 → 多数样本 `decisions:[]` → 练补漏 |
| **0.90**(立项书口径) | 30% | 95.6% 候选变 pending → 富含 decisions → 练复核 |

3200 条 gold × 1.3 ≈ **4200 个训练实例**。最终形态:补漏单独 ≈ 55%,补漏+复核共存 ≈ 25%,两者都空 ≈ 20%。

### prompt 多样性(防固化)

训练数据里 prompt 本身要变:`user_requirement` 不能全是「未提供额外要求」;`entity_types` 偶尔只给子集;候选密度由双阈值覆盖。

## 十三、训练配置

```yaml
base_model:      Qwen/Qwen3-14B        # BF16，QLoRA 在线量化成 NF4
                                        # 不是 -Base，不是 -AWQ
quantization:    nf4 (bitsandbytes)
lora_r:          32
lora_alpha:      64
lora_dropout:    0.05
target_modules:  [q_proj,k_proj,v_proj,o_proj,gate_proj,up_proj,down_proj]
                 # 不动 embedding / lm_head
learning_rate:   1e-4
lr_scheduler:    cosine
warmup_ratio:    0.03
num_epochs:      3                      # 每 epoch 存 checkpoint
max_seq_len:     3072
per_device_bs:   2
grad_accum:      4                      # 有效 batch 8
bf16:            true
gradient_checkpointing: true
train_on_completions_only: true         # loss 只算 assistant 部分
```

`max_seq_len=3072` 的依据：英文 prompt 现已被 8 句上限封顶（约 409 token），
中文最坏为 1200 字 fallback（约 1500 token）。3072 是余量，配合动态 padding
对短样本几乎无成本；而序列被静默截断的代价远高于余量成本。

显存:NF4 基座约 8GB + LoRA 梯度/优化器约 2GB + 激活约 4GB ≈ **15GB**,A100 40G 富余。

**选 checkpoint 不选最后一个** —— 三个 epoch 各评一次 dev,选最好的。这是防固化最实用的一条。

## 十四、部署

vLLM 支持在不 merge 的情况下把 LoRA adapter 挂到 AWQ 基座上。

```bash
vllm serve /root/qwen3-14b-awq \
  --served-model-name privshield \
  --host 0.0.0.0 --port 8000 \
  --enable-lora --lora-modules privshield=/mnt/adapter \
  --max-lora-rank 32 --max-model-len 4096
```

后端只改 `.env` 一行:`PRIVSHIELD_LLM_MODEL=privshield`。**代码零改动。**

`--host 0.0.0.0` 必须有,否则矩池云端口导出访问不到。**端口导出要在租机器时的「高级配置」里填,机器起来之后加不了。**

**必测:** QLoRA 在 NF4 上训、部署挂 AWQ,两种量化误差分布不同。同一 adapter 在两个基座各评一次。衰减大就退回 bitsandbytes NF4 基座——仍是 4-bit、仍本地、仍只改配置。

## 十五、唯一的后端改动:find-all

```python
# llm_adapter.py 中 additions 的落地
for item in parsed.additions:
    for s, e in find_all(text, item.text):   # 所有出现位置
        ...
```

**这是修 bug,不是加功能。** 实测:规则层用 regex `finditer` 天然找全部出现,LLM 补漏却只加模型指的那一个位置。「张伟」在文中出现于 0、18、42,模型报了 0,**18 和 42 原封不动留在脱敏输出里**。隐私工具里这是漏网。

两个护栏(已在 `primitives.find_all()` 实现并验证):surface 长度 < 2 不做 find-all;拉丁串要词边界(`find("Li")` 不得命中 `Lisbon`)。

副作用是好的:**偏移从「成败关键」降级为「诊断指标」**。原本一条偏移错 → 整个响应作废 → 重试 2 次 → 整层降级、连正确的 decisions 一起丢。

**训练目标仍然带正确偏移** —— gold 里白拿的,不多花一个 token,还白送一个指标。

## 十六、API 预算与止损

| 项 | 值 |
|---|---|
| 单样本重试上限 | 3 |
| 同一错误签名连续失败 | 3 次即停止 |
| 全局调用上限 | 2500 |
| 全局墙钟上限 | 7200 秒 |
| 总预算 | **¥150** |

每次调用必须记录:model、attempt、latency、input/output token、error signature、是否成功。

**省钱姿势:长档用好模型(稀疏度约束最难),短档用便宜模型。** 全用顶档约 ¥130,分档后约 ¥70。

生成模型不预先指定,**pilot 阶段跑 bake-off 决定**:4 个候选各 16 条,比解析良品率 / 稀疏度合规率 / 漏标率 / distinct-4gram / 人眼自然度。全部避开 thinking 版本(推理过程吃光预算、content 返回空,是已记录的原始故障)。

**主力应该是非 Qwen 的** —— 微调目标是 Qwen3-14B,生成也全用 Qwen 就是自蒸馏,「对它来说本来就简单」的样本会被系统性过采样。

## 十七、评测

比对口径是 **(surface, label) 集合**,不是 (start, end, label) —— find-all 之后同一个串的所有出现都会被打码,位置不再是判据。

**主指标**(冻结测试集 600 条):实体级 P/R/F1;分标签(9 类);**分语种**(英文大概率更差,不分开报你自己都不知道);分长度档;**按 trap 类型的误报率**。

**三条基线,同一测试集:**

| | 配置 |
|---|---|
| B0 | 不接第三层(规则 + NER-LITE) |
| B1 | 接**未微调**的 Qwen3-14B-AWQ |
| B2 | 接**微调后**的 |

**B2 − B1 是微调的贡献,B1 − B0 是第三层的贡献。报 delta,不报孤立数字。**

**诊断指标:** JSON 解析成功率(> 99%);**id 回抄准确率**(模型要原样复制 `span_a1b2c3d4e5` 这种 10 位随机 hex,抄错那条决策被 `by_id.get()` 静默丢弃);偏移精确匹配率;平均延迟。

**指令跟随测试:** 给一个训练时没出现过的 `user_requirement`。掉得厉害就是过拟合的直接证据。

**外部探针:** CLUENER dev 上的 ORG / LOCATION / ADDRESS 召回。**不报 PERSON** —— CLUENER 把公众人物、历史人物一律标 `name`,而本项目口径里这些是硬负样本,语义冲突。写明这是跨数据集泛化探针。

## 十八、关键决策与依据

| 决策 | 依据 |
|---|---|
| 不用 CLUENER 做训练 | 它把公众人物标 `name`,与本项目硬负样本口径冲突 |
| 排除 `CUSTOM` | 运行时填充、恒 1.0 采纳,永不成为候选 |
| 校验位从可选变必须 | 非法值被规则层静默丢弃,训练分布与线上相反 |
| find-all 落地 | 规则层已 find-all,LLM 补漏只加一处,其余出现漏网 |
| 偏移仍训但降级为诊断 | gold 里白拿,不额外花 token,还送一个指标 |
| 双阈值派生 | 队友何时开 BERT NER / 改阈值都不用重训 |
| 生成/派生分层 | 上一轮「改一次标注规范全部重来」的直接对策 |
| 丢弃优先于修复 | 反馈式重试导致模板坍缩,25 次连续失败产出 0 条 |
| 主力用非 Qwen 生成 | 避免自蒸馏,防止难样本被系统性过采样 |
| 长档权重 30% | 真实文本与合成文本的 PII 密度差两个数量级 |

## 十九、已知局限(须在最终报告中如实记录)

1. **训练数据全为合成**,存在生成模型的文风先验;同源测试集数字会系统性偏高,故配 CLUENER 外部探针
2. **英文样本不含 ID_CARD**,后端正则为中国身份证专用
3. **跨句准标识符组合**(年龄 + 职业 + 地区可定位到人)不在 v1 范围
4. **`routed_context` 的窗口限制**:长文档中窗口外的实体模型看不到,已实测某长文档可见率仅 3.0%。这是路由层的结构性上限,不是模型能力问题,评测时分开归因
5. **`trap_spans` 的陷阱类型由人枚举**,不覆盖全部真实误报模式
6. **NF4 训练 → AWQ 部署**存在量化迁移损失,已测量并记录
